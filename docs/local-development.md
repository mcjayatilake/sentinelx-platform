# Local Development — Database

Commands for working with PostgreSQL, Alembic, and the test database
locally. All commands assume `backend/` as the working directory unless
run through `make`/`docker compose` from the repo root.

## Starting the database

Via Docker Compose (recommended — see the root `README.md`):

```bash
cp .env.example .env
make up          # starts postgres, redis, minio, backend, worker, beat, flower, frontend
```

## Running migrations

```bash
make migrate                                    # alembic upgrade head, inside the backend container
make migrate-generate name="add scan retries"    # alembic revision --autogenerate -m "..."
```

Or directly, from `backend/` with a local virtualenv and `DATABASE_URL_SYNC`
pointed at your database:

```bash
alembic upgrade head
alembic downgrade -1        # step back one migration
alembic downgrade base      # drop everything this project's migrations created
alembic current              # show the currently-applied revision
alembic history               # show the migration chain
```

**Always review an autogenerated migration before committing it** — open
the generated file in `backend/alembic/versions/` and check it against the
models that changed. Autogenerate has real blind spots (see
[`database-architecture.md`](database-architecture.md) for two concrete
bugs this caught during development): it won't always catch every
constraint change, and it will never verify a `CHECK` constraint's SQL text
is correct — that's on you to read.

## Seed data

```bash
make seed          # python -m app.db.seed, inside the backend container
```

- Creates one dev tenant (`sentinelx-dev`), one dev user
  (`dev-seed@sentinelx.local`), a membership, and one project
  (`sample-project`) — all clearly labeled as seed data in their names.
- Safe to run repeatedly (idempotent — reuses existing rows by slug/email).
- Refuses to run when `ENVIRONMENT=production`.

## Running tests

The test suite runs against **real PostgreSQL**, not SQLite — most of what
it verifies (composite foreign keys, `CHECK`-constraint enums, `JSONB` size
limits) is PostgreSQL-specific behavior a SQLite run wouldn't actually
test.

```bash
# Inside the backend container / a venv with DATABASE_URL pointed at a
# PostgreSQL instance the test suite is allowed to create/drop tables in:
pytest                              # full suite
pytest --cov=app --cov-report=term-missing   # with coverage
pytest tests/test_finding_repository.py -v    # one file
```

What happens automatically:

- A session-scoped `autouse` fixture (`_run_migrations` in
  `tests/conftest.py`) runs `alembic upgrade head` against
  `DATABASE_URL`/`DATABASE_URL_SYNC` once per test run. It's idempotent —
  a database already at `head` is a no-op, so you don't need to reset
  anything between runs.
- Each test gets its own `db_session` fixture: a connection-level
  transaction that's always rolled back at teardown
  (`join_transaction_mode="create_savepoint"`), so tests never leak data
  into each other and never need manual cleanup.
- `db_engine` is function-scoped, not session-scoped — deliberately, to
  avoid a known pytest-asyncio pitfall where a session-scoped async engine
  gets bound to the first test's event loop and breaks on every test after
  it. See the comment in `tests/conftest.py` if you're tempted to "optimize"
  this back to session scope.

### Environment variables the test suite needs

```bash
DATABASE_URL=postgresql+asyncpg://sentinelx:sentinelx@localhost:5432/sentinelx_test
DATABASE_URL_SYNC=postgresql+psycopg://sentinelx:sentinelx@localhost:5432/sentinelx_test
JWT_SECRET_KEY=test-secret
REDIS_URL=redis://localhost:6379/0   # only needed for the readiness-endpoint tests
```

CI (`.github/workflows/backend-ci.yml`) provisions a `postgres:16-alpine`
and `redis:7-alpine` service container with matching credentials — see
that file for the exact values if you want your local setup to match
exactly.

## Direct database access

```bash
make db-shell        # psql against the postgres container
```

Or directly: `psql -h localhost -U sentinelx -d sentinelx`.

## Common issues

- **`InvalidForeignKey: there is no unique constraint matching given keys`**
  on `alembic upgrade head` — a composite foreign key references
  `(tenant_id, id)` on a parent table that's missing the matching
  `UNIQUE (tenant_id, id)` constraint. Every table referenced by a
  composite tenant-propagating FK needs that constraint declared on it —
  see `tenant-isolation.md`.
- **A duplicate-value test doesn't raise `IntegrityError`** — check the
  enum column actually has `create_constraint=True` (not just
  `native_enum=False`); without it, no `CHECK` constraint is created at
  all. See `database-architecture.md`.
